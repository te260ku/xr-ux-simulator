# ヘキサゴナルアーキテクチャ 採用理由書

対象：Unity Windows アプリ（Timeline / Reactive / 外部機器連携）     2026年10月29日

文書区分：アーキテクチャ選定理由書（採用方針の記録／効果の実測は未完了）

**設計判断** アプリケーションの中核と入出力の具体実装を分離する基本構造として、ヘキサゴナルアーキテクチャ（Ports & Adapters）を採用する。

## 1. 目的と判断方法

本書は、複数の外部CSライブラリ、UI、タイムライン実行、条件駆動処理を持つUnityアプリについて、採用アーキテクチャと代替案の選定根拠を記録する。

Michael Keeling『Design It!』に従い、アーキテクチャ上重要な要求（ASR）を整理し、候補を定性的なDecision Matrixで比較する。採用理由だけでなく、受け入れる欠点・適用境界・確認方法も明記する。

## 2. 判断の前提：ASR（アーキテクチャ上重要な要求）

下表は現在判明している要件から整理した選定用ASR。重み・数値目標は未確定であり、達成を実証した一覧ではない。

| ID / 種別 | 要求・制約 | 設計への影響 |
| --- | --- | --- |
| ASR-01（変更容易性） | 外部CSライブラリ、UI実装、出力デバイスの変更を想定する。 | 外部実装への依存を狭い境界に閉じ込める。 |
| ASR-02（テスト容易性） | 実機・外部システムなしでも中核処理を自動検証したい。 | 出力を代替実装に差し替え、入力を疑似的に再現できるようにする。 |
| ASR-03（機能的要求） | TimelineとReactiveで同じコマンド実行処理を利用する。 | 実行契機とアクチュエーションを分離する。 |
| ASR-04（変更容易性） | 入力取得、UI表示、外部への音・光・座標出力をそれぞれ独立に改修する。 | Updater、Coordinator、Presenter/View、Controllerの責務を分ける。 |
| ASR-05（運用性） | 画像・音声・設定等の一部はビルド後に変更する。 | ファイル管理・ロードをアプリの判断処理から分離する。 |
| ASR-06（性能・信頼性） | 連続座標更新、タイムラインの時刻実行、外部通信を扱う。 | 抽象化の採用だけで成立しない。遅延・欠落・メモリを実測する。 |
| 制約（技術） | Unity / Windows / C# 9 / VContainer / 既存CSライブラリ。 | 既存環境を前提に過度な実装変更を避ける。 |

## 3. 比較対象

**案A：直接結合型** Updater、Coordinator、Controllerが具体クラスを直接参照する。構築は簡単だが、外部実装の知識が中核に入り込みやすい。

**案B：一般的なレイヤード型** UI／アプリケーション／インフラを責務別に分割するが、アプリケーション層から具体的なインフラ実装への参照を許容する構成として比較する。

**案C：ヘキサゴナル型** Coreがユースケースと出力Portを定義し、外側のAdapterがPortを実装する。入力AdapterはCoreの公開APIを呼び出す。

注意：レイヤード型でもDIPを徹底すればCと近い構造を実現できる。両者は排他的ではない。Publish–Subscribeは通信・協調様式であり、今回の3案と併用できる。

## 4. アーキテクチャ比較表（Decision Matrix）

評価は設計上の相対的な見通しであり、測定値ではない。記号：◎ 適合しやすい／○ 適合可能／△ 工夫が必要。

| 評価基準（ASR） | 案A 直接結合 | 案B レイヤード | 案C ヘキサゴナル |
| --- | --- | --- | --- |
| 外部入出力の変更局所化（ASR-01,04） | △ 具体型の参照が中核へ波及しやすい | ○ 層別の分離で一定の局所化が可能 | ◎ Coreが外部実装を参照しない構成を徹底できる |
| 実機なしの中核テスト（ASR-02） | △ スタブ化のため依存を改修する場合がある | ○ DI設計次第で実施可能 | ◎ PortへのFake注入を設計時から想定できる |
| Timeline/Reactiveの共通化（ASR-03） | ○ 独立した共通APIを設ければ可能 | ○ サービスの分割で可能 | ○ アプリ層に共通実行機能を配置できる |
| ビルド後の資産更新（ASR-05） | ○ ファイル管理の分離次第 | ○ インフラ分割で可能 | ○ Adapterとして分離可能。方式自体の優位差は小さい |
| 実行時性能（ASR-06） | ○ 構造が単純 | ○ 実装次第 | ○ 境界の呼出しコストはあるが、合否は実測で判断 |
| 実装・学習コスト | ◎ 定義が少ない | ○ 中程度 | △ PortとDIの設計・運用が増える |
| 責務境界の明確さ（ASR-01,04） | △ 個別の規約に依存 | ○ 層構造として示せる | ◎ 何がCoreに依存してよいかを明文化できる |

総合判断：変更容易性・テスト容易性・依存方向の明確化を重視し、案Cを選定する。一方、初期実装量と理解負荷については案A・Bが有利であり、全領域にPortを機械的に追加しない。

## 5. 採用判断の具体的根拠

### 5.1 外部音声制御ライブラリを変更する場合

案AではCoordinatorが具体的なCSライブラリAPIやController実装を知ると、そのAPI変更がCoordinatorまで波及しうる。案CではCoordinatorはISoundController等の出力Portに依存し、変更はSoundControllerと外部ライブラリ境界へ集中する。Portの契約が維持されることが前提であり、再生仕様そのものの変更はCoreにも及ぶ。

### 5.2 センサーを接続せず動作試験する場合

入力Adapterをテスト用データ源に置き換え、出力PortにFakeを接続する。Coordinator、Timeline、Reactiveの判断・命令順序を実機なしで検証できる。案BでもDIとインターフェースを適切に採れば同等の効果は得られるが、案Cはその境界を主要な構造として定義する点が異なる。

### 5.3 座標CSライブラリのデータ型が変更される場合

RawPositionのプロパティ名の変更など、表現の差はUpdaterで吸収できる。ただし、Coreが必要とするパラメータや意味も変更されるなら、Coordinatorやドメインの修正が必要である。ライブラリ型の複製を一律に義務付けるのではなく、独立させる価値のある境界で変換を行う。

### 5.4 新しいアクチュエーションが必要になる場合

外部機器用Adapterの追加は局所化できるが、新たな出力を「いつ、どの条件で」実行するかのユースケースが変わるならCoordinatorも変更する。ヘキサゴナル型は要求変更をなくすものではなく、外部実装の変更と業務上の判断変更を区別しやすくする。

## 6. 今回のコンポーネント群への適用

| コンポーネント群 | 配置・役割 | 依存関係の原則 |
| --- | --- | --- |
| Updater | Driving Adapter：CSライブラリの値やイベントを取得 | CoreのCoordinator公開APIを呼ぶ。入力Portのinterfaceは必要時のみ。 |
| Coordinator | Application Service：ユースケース・処理の調整 | 出力側の具体実装ではなく、Coreに定義したPortへ依存。 |
| Presenter / View | UI Adapter：表示変換、uGUIの操作、UI入力 | Presenter/Viewの内部構成は独立に設計。CoreへUI固有型を持ち込まない。 |
| Actuation Controller | Driven Adapter：音・光・外部送信などを実行 | 必要な出力Portを実装し、CSライブラリへ接続。 |
| Repository / Loader | リソース定義・パス解決・取得・キャッシュ | ビルド後の更新と、Coreに必要な契約を分離する。 |

依存方向（例）：PositionUpdater → PositionCoordinator → IPositionDisplay ← PositionPresenter → PositionView。実行時にCoordinatorがPresenterを呼ぶ場合でも、コンパイル時の依存はPortへ向ける。

## 7. 受け入れるトレードオフと適用ルール

| 受け入れる負担・リスク | 対応方針 |
| --- | --- |
| Port・抽象化によるクラス数増加 | Coreが外部実装を参照する境界や、実機差し替えが必要な境界を優先。クラスごとの機械的なinterface追加はしない。 |
| DTO変換・境界マッピングの重複 | 表現・意味の独立性が必要な場合のみ変換する。既存の安定した共有契約を使う判断も許容する。 |
| DI設定や起動経路が複雑化 | VContainerのComposition Rootで結線を集約し、起動テストで不足登録を検出する。 |
| 性能・実行順序の不確実性 | Unity ProfilerとWindows実機のシステムテストで、時間誤差・入力欠落・メモリ・GC等を検証する。 |

## 8. 適合性の検証計画

| 検証シナリオ | 観測すべき結果 | 方法 |
| --- | --- | --- |
| 外部音声CS APIを模擬的に変更 | Coordinatorの修正なしで連携側を変更できる | Adapter変更箇所レビュー、コンパイルテスト |
| 疑似座標入力による反応検証 | 実機なしで所定の出力指示が発行される | Updater置換／Fake Controllerによる自動テスト |
| TimelineとReactiveから同一コマンドを呼ぶ | 共通Executorで同一仕様の実行結果を得る | 両モードの結合テスト |
| 外部ファイルを差し替える | 規定の再起動／キャッシュ更新手順で反映される | Windowsビルドの受入テスト |
| 連続座標更新・高負荷実行 | 運用上必要な処理遅延・安定性を満たす | Unity Profilerと通常ビルドによる計測 |

性能・時間誤差の数値閾値、対象デバイス構成、連続稼働時間は別途ASRで確定する。本書はそれらを合格済みとは扱わない。

## 9. 最終判断

複数の外部システムを入出力に持ち、機器がなくても中核機能を試験したい本アプリでは、CoreとAdapterの依存方向を明確にすることが保守・検証に有利である。そのため基本アーキテクチャとしてヘキサゴナル型を採用する。

ただし、レイヤード型を否定するものではない。Application内部は必要に応じてレイヤー化し、UI内部ではPresenter/Viewを使用する。機能内通信は直接呼び出しを基本とし、R3などのイベント機構は明確な必要がある箇所に限定する。

本判断は設計上の見通しであり、実証済みの効果ではない。上記の変更シナリオとテスト結果をもって、期待した変更容易性・テスト容易性を検証する。
